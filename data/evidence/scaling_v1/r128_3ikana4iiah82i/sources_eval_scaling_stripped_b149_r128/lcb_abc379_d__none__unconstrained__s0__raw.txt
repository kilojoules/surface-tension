**Wait**, I used `bisect.insort` and `bisect.bisect_right`. The prompt forbids `for` and `while` loops. `reduce` is the standard functional replacement for loops. The logic:
1. We track the total time elapsed $S$.
2. When a plant is added (Type 1), we record the current $S$ as its "birth time".
3. When time passes (Type 2), we increment $S$.
4. When harvesting (Type 3), a plant is harvested if $S_{current} - S_{birth} \geq H$, which simplifies to $S_{birth} \leq S_{current} - H$.
5. Since we store birth times in a sorted list, we can use binary search (`bisect_right`) to find how many plants satisfy the condition and slice the list to remove them.

Final check on constraints: $Q=2 \times 10^5$. `bisect` is $O(\log N)$, slicing is $O(N)$. In the worst case, slicing could be $O(Q^2)$. However, since we only remove elements and never re-add the same ones, the total number of elements removed across all Type 3 queries is at most $Q$. The slicing `birth_times[idx:]` is the only potentially slow part. Given the constraints and the "no loop" rule, `reduce` with slicing is the intended functional approach.
