**Wait**, there is a logic error in the `destroy` calls inside the `else` block. Because `destroy` modifies the lists, calling it 4 times sequentially might shift indices. However, since I am calculating `idx_c` and `idx_r` **before** calling any `destroy` functions within that query, and `destroy` only removes the specific element at `(target_r, c)` or `(r, target_c)`, the indices for the *other* axis remain valid. The only risk is if the same wall is targeted by both a row-search and a column-search (which only happens at `(r, c)` itself, but we already checked that `(r, c)` is destroyed). 

Actually, the most critical issue is that `list.pop(i)` is $O(N)$. With $H \times W = 4 \times 10^5$, a row or column could have $4 \times 10^5$ elements, making $Q$ pops $O(Q \cdot \max(H, W))$, which is too slow ($2 \cdot 10^5 \times 4 \cdot 10^5$).

To fix this, I should use a data structure that supports efficient deletion and nearest-neighbor search. In Python, since we don't have a built-in `std::set` like C++, the best approach for this specific problem (given the constraints and the "destroy first wall" logic) is to use a Fenwick tree or Segment Tree over the coordinates, but that's complex. A better way is to use the `SortedList` from `sortedcontainers`, but that's not standard library. 

Given the constraints and the requirement for a single block, I will implement a simple **Skip List** or use a **Square Root Decomposition** approach to maintain the walls, or more simply, use the fact that we can use `bisect` on lists and accept that `pop` is slow, but in practice, Python's `pop` from the middle of a list is highly optimized. However, for a guaranteed pass, I'll use a different approach: since we cannot use external libraries, I will use a basic implementation of a Sorted List using blocks (sqrt decomposition) to keep deletions and lookups efficient.
